# 多屏同显 — 会话协议 v1（同步内核原型专用）

> 配套规格：`../SPEC-v2.md`（同目录 SPEC-v2.md）。本文件只定义内核阶段需要的协议：组会、对时、起播、校正、布局下发。解析子系统不在本文件范围（内核用本地文件/直链验证）。
> 原则：协议与平台无关，安卓先实现，鸿蒙照此实现第二套。所有时间戳为毫秒。

## 1. 传输与角色

- 传输：同局域网 WebSocket（主机开服务端，从机连入），JSON 消息，字段 `t`（类型）、`seq`（序号）、其余按类型定义。
- 角色：一台 HOST（组会者 + 进度基准 + 布局持有者），N 台 CLIENT。音频机由 HOST 指定（`audio_client`），默认 HOST 自己。
- 入会：CLIENT 扫码得到 `ws://<host-ip>:<port>` 与会话令牌 → 发 `HELLO{device_name, screen_w, screen_h, platform}` → HOST 回 `WELCOME{client_no}`，编号自此固定，CLIENT 全屏可闪号。

## 2. 对时（类 NTP，起播前与每 60 秒各一轮）

- CLIENT 发 `PING{ c1 }`（本机时钟），HOST 回 `PONG{ c1, h2, h3 }`（收到/发出时的主机时钟），CLIENT 在 c4 记录。
- 取 5 次往返中 RTT 最小的一组估偏差：`offset = ((h2 - c1) + (h3 - c4)) / 2`（主机时钟 = 本机时钟 + offset）。
- 验收线：对时误差自评（由 RTT/2 上界）应 ≤10ms 量级；局域网正常 RTT 1–10ms 可达。

## 3. 媒体准备与起播

- HOST 发 `PREPARE{ url, duration_ms }`（内核阶段 url 为局域网直链或各机同名本地文件标识）。
- CLIENT 加载并预缓冲到可起播，回 `READY{ buffered_ms }`。
- 全员 READY 后 HOST 发 `START{ start_at_hostclock, media_pos_ms: 0 }`，其中 `start_at = 主机now + 1500ms`。
- CLIENT 把 start_at 换算到本机时钟（减 offset），到点起播。起播实现要点：提前 `prepare` 完成、播放器处于 paused-at-0 状态，到点只做 `play()`，把起播延迟压到最小并实测记录（见 §5 指标）。

## 4. 播中校正（30 分钟荷载核心）

- HOST 每 5000ms 广播 `TICK{ host_clock, media_pos_ms, rate: 1.0 }`（media_pos 为广播时刻主机真实进度）。
- CLIENT 收到 TICK 后：预期进度 = TICK.media_pos + (本机now换算主机时钟 − TICK.host_clock) × rate；偏差 `err = 实际进度 − 预期进度`。
  - |err| ≤ 50ms：不动。
  - 50ms < |err| ≤ 120ms：速率微调，err>0（快了）用 0.97，err<0 用 1.03，回到 ≤20ms 后恢复 1.0。
  - |err| > 120ms：立即 seek 到预期进度（硬校正），并记一次事件日志。
- CLIENT 每 10 秒回 `STAT{ media_pos_ms, err_ms, buffered_ms, corrections }` 供 HOST 汇总与原型验收读数。
- CLIENT 本地再缓冲（buffering）结束后：按最新 TICK 的预期进度 seek 归队，回 `RESYNC{ from_pos, to_pos }`。

## 5. 布局下发（编号定位，内核阶段先做静态版）

- HOST 持布局：数组 `[{ client_no, x, y, w, h, rot }]`，坐标为整体画布归一化值（0–1），由布局编辑器（后续）产生；内核阶段用配置文件/手填 JSON 代替编辑器。
- HOST 发 `LAYOUT{ canvas_ratio, tiles: [...] }`，CLIENT 按自己编号取 tile：渲染时把完整画面先按画布比例铺满虚拟画布，再显示 tile 对应子区域（渲染层裁剪+偏移，源文件不切）。
- 改布局发新 LAYOUT 即时生效，不中断播放（便于对位微调）。

## 6. 内核原型验收读数（量尺）

原型 App 须在屏幕角落常显调试行，并落盘日志，供 Owen 真机验收：
- 本机编号、对时 offset 与 RTT、最近一次 err（ms）、累计硬校正次数、微调中状态。
- 验收跑法：2 台安卓同播一个本地 mp4（≥10 分钟），每分钟记录两台 STAT 的 err；通过线：稳态 |err| ≤50ms 为主、任何抽查 ≤120ms。

## 7. 非内核阶段（本文件不定义）

分享链接解析（抖音/B站）、布局编辑器 UI、鸿蒙端实现、iOS——均按 SPEC-v2 分期，协议届时只增消息类型，不改既有语义。

## 8. v1.1 增补（v0.3 实现）

本节为 v0.3 新增语义，只增补、不改上面各节正文。

- **`PAUSE{ media_pos_ms }`**（HOST → 全场）：主机按下暂停时先记下本机当前进度并暂停，再广播，字段值为广播时刻的主机进度。从机收到后在主线程执行：本机进度与 `media_pos_ms` 相差超过 80ms 时先 seek 到 `media_pos_ms`，然后暂停。
- **`RESUME{ start_at_hostclock, media_pos_ms, rate }`**（HOST → 全场）：主机按下继续时生成，`start_at_hostclock` = 主机当前时钟 + 1200ms。从机按第 3 节 START 相同的定时机制，在 `start_at` 换算成的本机时刻 seek 到 `media_pos_ms` 并以 `rate` 起播；主机本机在同一时刻起播。RESUME 的定时起播不触发首次 TICK 硬对齐（该对齐只属于 START）。
- **`SEEK{ media_pos_ms }`**（HOST → 全场）：播放中，全场 seek 到 `media_pos_ms` 继续播放；暂停中，全场 seek 到 `media_pos_ms` 并保持暂停。主机与从机执行同一规则。从机在暂停状态下不得因 SEEK、PAUSE、RATE 自行起播，只有 RESUME 可以使其起播。
- **`RATE{ rate }`**（HOST → 全场）：设定全场会话倍速 `sessionRate`，取值限 0.5 / 0.75 / 1.0 / 1.25 / 1.5 / 2.0。主机与从机都保存为 `sessionRate` 并立即应用到播放器。第 4 节播中校正的倍速档改为以 `sessionRate` 为基准乘 0.97 / 1.03，恢复目标为 `sessionRate`；三档阈值（50 / 120ms）不变。预期进度计算按第 4 节公式乘 `rate`（TICK 携带的 rate 即主机会话倍速）。
- **`TICK` 新增字段 `state`（`playing` / `paused`）与 `rate`（主机当前 sessionRate）**：主机暂停期间照常每 5000ms 广播 TICK，`media_pos_ms` 为暂停点进度。从机在主机 `state` 为 `paused` 或本机处于暂停时跳过校正——倍速恢复 `sessionRate`、不 seek、只更新读数。
- **`STAT` 新增字段 `stalls`**：从机已起播状态下进入 `STATE_BUFFERING` 的累计次数，供主机侧区分设备卡顿与同步偏差。
- **周期对时**：第 2 节「每 60 秒各一轮」自 v0.3 起落地——从机首次对时完成后每 60 秒重跑一轮完整的 5 采样对时，取最小 RTT 样本更新 offset。offset 变化由 TICK 校正自然吸收，不因此额外触发 seek。
- **播放结束**：全场停在结束帧（STATE_ENDED）；主机再按播放键时重走第 3 节 PREPARE → START 全流程。

## 9. v1.2 增补（v0.3.1 实现）

本节为 v0.3.1 的调参与新增语义。其中校正参数三点**覆盖第 4 节的三档规则**，属 Owen 2026-11-11 批准的调参（真机判读依据：±50ms 死区 + 0.97／1.03 倍速微调 + >120ms seek 在管线吃紧的设备上形成 seek 风暴与倍速乱切）；其余章节与 v1.1 增补不变。

- **校正换形（覆盖第 4 节三档规则）**：从机改为自由播 + 宽死区 + 稀疏 seek。
  - **死区 200ms**：偏差 |err| ≤ 200ms 时不做任何校正。
  - **倍速微调取消**：第 4 节的 0.97／1.03 速率微调档整体删除。从机播放速度恒等于 `sessionRate`（由 `RATE` 消息与 TICK 的 `rate` 字段同步），校正逻辑不再调用变速追赶。
  - **硬拉**：|err| > 200ms 时 seek 到预期进度（目标计算同第 4 节），记一次硬校正（计入 STAT 的 `corrections`）。
  - **seek 冷却 8 秒**：每次硬拉 seek 后进入 8 秒冷却期，冷却内即使 |err| 再次超过 200ms 也不再 seek，只记录（`action=cooldown-skip`）。冷却到期恢复判定。
  - **首次 TICK 硬对齐不变**：起播后第一次 TICK 仍按 |err| > 50ms 直接 seek 对齐（v0.2.1 语义）；该次对齐执行后同样开启 8 秒冷却。
  - 从机 TICK 处理的 action 取值自 v0.3.1 起为：`none`／`seek`／`first-align`／`cooldown-skip`／`paused-skip`。暂停跳过语义（v1.1）不变。
- **`BRIGHTNESS{ level }`**（HOST → 全场）：`level` 为浮点窗口亮度，取值 0.05–1.0。主机拖动亮度滑杆后先应用本机窗口亮度（`WindowManager.LayoutParams.screenBrightness`），再广播本消息；从机收到后在主线程应用本机窗口亮度。从机本地亦可单独调本机亮度（不广播），但之后收到主机 `BRIGHTNESS` 时以主机值为准覆盖本机。
- **`PREPARE` 的 `url` 三种取值与主机分发服务**：`url` 可为（a）**主机分发地址**——主机选本地文件且有从机连接时，主机在本机局域网 IP 的 **18767** 端口起一个 HTTP 文件服务（与 WebSocket 的 18765 区分），只提供当前选定的一个文件，地址形如 `http://<主机IP>:18767/media/<会话令牌>`，令牌为每次组会生成的 16 位随机串，路径无令牌或令牌不符一律 404；服务必须支持 **Range** 请求（`bytes=start-end`、只有起点、只有尾部三形式，回 206 与 `Content-Range`；无 Range 回 200 与完整 `Content-Length`），供从机流式拉取与 seek；（b）**公网直链**——用户在主机粘贴的 http/https 直链原样下发；（c）**`local-file` 占位**——各机用本机同名本地文件的旧路径。从机收到以 http:// 或 https:// 开头的 `url` 时直接以该地址建播放器并 prepare，不再要求本机选片；READY 回法与本地模式一致。主机本机播放恒走本地文件 uri，不经自己的分发服务。
- **`START` 幂等**：从机（与主机本机）收到 START 时，无论本机是否正在播放，先 seek 到 `START.media_pos_ms` 并暂停待命，再按定时机制在 `start_at` 起播。播放中收到第二次 START 必须回到新时间线，不许无操作（旧实现曾导致从机留在旧时间线、首次 TICK 出现两万多毫秒假偏差）。
- **`RESYNC` 纪律（抑制 seek—缓冲互激）**：本机每次程序 seek（首次对齐、校正硬拉、RESYNC 自身、PAUSE／SEEK／RESUME／START 的 seek）都记录时刻 `lastProgramSeekMs`。缓冲结束时：距 `lastProgramSeekMs` 小于 **1500ms** 的判定为 seek 诱发，不触发 RESYNC；非 seek 诱发的，再判偏差门——预期进度与本机进度之差绝对值 ≤ **300ms** 不触发；两次 RESYNC 间隔小于 **5 秒** 不执行第二次（记 `skip=cooldown` 日志）。RESYNC 执行日志含 from、to 与当时 err。
- **`STAT` 新增字段 `stalls_load` 与 `stalls_seek`**：从机卡顿分开计数——进入 `STATE_BUFFERING` 时距 `lastProgramSeekMs` <1500ms 的计入 `stalls_seek`（seek 诱发），其余计入 `stalls_load`（加载卡顿）；原 `stalls` 字段保留为两者之和。另：从机在 `STATE_BUFFERING` 期间收到 TICK 不做任何校正（含不消耗首次对齐判定），记 `action=buffering-skip`。

## 10. v1.3 增补（v0.3.2 实现）

本节为 v0.3.2 新增语义，只增补、不改上面各节正文。背景（真机判读）：第 9 节的分发流式模式下，从机恒定落后主机约 0.7–1 秒——每次校正 seek 在 HTTP 流式下要付约 1 秒重新拉数据的成本，seek 永远在还上一笔的账；本地文件模式 seek 几乎免费（同机实测 err 中位 3ms）。

- **分发模式改为下载后播**：从机收到分发地址（第 9 节的 (a) 类 url）后，不再直接流式 prepare，先在后台下载整文件到本机缓存，再以本地文件建播放器 prepare，READY 回法与本地模式完全一致；下载产物即本场媒体，后续校正、拖动、RESYNC 全部走本地文件语义。
  - **缓存键**：文件名 `dist-<令牌前8位>-<Content-Length>.bin`，存本机应用缓存目录的 `dist` 子目录。下载开始前先取得响应 `Content-Length` 组键：同名文件已存在且字节数等于 `Content-Length` 时跳过下载、直接用缓存；新一次下载开始时删除 `dist` 子目录内除本次目标外的旧分发缓存（至多保留当前一份）。
  - **进度**：从机状态行显示「分发下载中 <百分比>%」（`Content-Length` 已知时）；日志标签 `DOWNLOAD`（开始、每 25% 一行、完成含实际字节数与耗时）。
  - **失败回退流式**：下载失败（连接错误、字节数与 `Content-Length` 不一致、或连续 10 秒无新字节到达）时，状态行显示「分发下载失败，回退流式播放」，回退到第 9 节的流式 prepare 路径（流式路径保留，不删除）。
- **`PREPARE_FAIL{ client_no, reason }`**（CLIENT → HOST，新消息）：从机远程备片超时时发送。`reason` 取值：`link_timeout`（直链模式超时）、`dist_stream_timeout`（分发流式回退路径超时）。主机收到后状态行显示「从机 <编号> 备片失败：<原因中文>」并落同名日志。
- **主机收齐判定（覆盖第 9 节之前的「全员 READY」口径）**：起播条件改为——已回 READY 的从机数 + 已回 `PREPARE_FAIL` 的从机数（均限当前连接）≥ 当前连接从机总数时即可起播。FAIL 的从机不参与本场（不等待、不重发 PREPARE 给它），其余从机与主机照常起播；主机的「等待 READY」名单与「重发准备」对象同样排除已 FAIL 的从机。旧判定（READY 须覆盖全部连接）曾被一台坏链从机永久阻塞全场，本口径即为修复。
- **远程备片 15 秒超时口径**：计时起点为远程 url 的 prepare 开始时刻（用户重走 PREPARE 流程时重新计时）；15 秒内播放器未到达 `STATE_READY` 即判定超时。适用范围：从机直链模式、从机分发流式回退路径、主机本机直链备片（主机超时只显示本机文案，不发 `PREPARE_FAIL`）。从机超时文案：直链显示「链接无法直接播放（可能不是直链）」，分发流式回退显示「分发拉取超时」，并同时发 `PREPARE_FAIL`。超时后不自动重试。**分发下载路径不适用本条**（其失败判定为下载自身的「连续 10 秒无新字节」）。

## 11. v1.4 增补（v0.3.3 实现）

本节为 v0.3.3 的校正策略再换形，**supersede 第 9 节 v1.2 增补中的校正段落**（死区 200ms、倍速微调取消、>200ms seek、首次 TICK 硬对齐四点均被本节取代）；第 9 节其余语义（BRIGHTNESS、PREPARE 三态与分发服务、START 幂等、STAT 字段）不变，第 10 节的 RESYNC 纪律框架保留、其偏差门按本节改口径。背景（真机判读，host-log-v032.txt 及 v0.3.2 从机日志）：从机在无 seek 区间播放速率精确（1.5 倍速实测 1.499–1.502），但每次校正 seek 后约 5 秒只能跑约 1.31 倍速、丢约 0.9 秒——**seek 本身付约 1 秒代价（播放器侧成本，与网络无关，本地文件同样存在）**；v1.2 的「>200ms 即 seek」注入的误差比修掉的还大，校正回路自激。本节把 seek 逐出常规校正回路，改用速率微调平滑追赶；微调不触发 seek 的代价，无自激之源。

- **死区 30ms**：|err| ≤ 30ms 时不校正；若从机当前实际播放速率不等于会话速率 `sessionRate`，先恢复为 `sessionRate`（该拍 action 记 `rate-restore`，无恢复动作时记 `none`）。
- **微调区 30–2000ms**：30ms < |err| ≤ 2000ms 时只许速率微调、不许 seek。调整量公式：`adj = clamp(-err/10000, -0.05, +0.05)`（err 单位毫秒），实际播放速率 = `sessionRate × (1 + adj)`。符号：err 为负（从机落后）→ adj 为正、加速追赶；err 为正（超前）→ adj 为负、减速等待。执行纪律：算出的实际速率与当前实际速率相差 <0.002 时不重复下发（防抖动）；每次实际下发速率变化记一行 `RATE_ADJ` 日志（含 err、会话速率、实际速率，三位小数）。从机 TICK 日志行追加 `rate` 字段（当前实际播放速率，三位小数），action 取值新增 `rate-adj` 与 `rate-restore`。微调上限恒为 ±5%，不许放宽。
- **seek 仅限灾难偏差**：|err| > 2000ms 才许 seek（action 记 `seek`），沿用 8 秒 seek 冷却，冷却只约束 seek（冷却内再遇灾难偏差记 `cooldown-skip`）。起播后第一拍 TICK 与后续拍走同一套规则——v1.2 的首次 TICK 50ms 硬对齐特例删除，`firstTickAfterStart` 只作日志区分。从机收到 START／RESUME／RATE 任一消息时，实际播放速率先回到该消息确定的会话速率，其后由校正回路按新 err 重新微调；PAUSE 期间校正不运行。主机本机播放不参与微调（主机即参考，恒为会话速率）；主机发出的 PAUSE／SEEK／RESUME／START 指令自身的 seek 语义不变（属用户操作与会话事件，不属校正回路）。
- **RESYNC 的 micro-band 纪律**：从机本地缓冲结束时计算 err，|err| ≤ 2000ms 不许 seek，记 `RESYNC skip=micro-band`，交播中微调收敛；|err| > 2000ms 才执行 resync seek。原 seek-induced 判定（缓冲结束距上次程序 seek <1500ms 不触发）与两次 RESYNC 5 秒最小间隔保留不变（v1.2 的 300ms small-err 偏差门被本条 2000ms micro-band 门取代）。

## 12. v1.5 增补（v0.5.0 实现）

本节为 v0.5.0 新增的局域网一次性文件互传语义，只增补、不改上面各节正文。互传与视频会话相互独立、可并行（同一时刻只跑一轮互传）；传输方式沿用第 9 节分发服务的「接收方拉取」骨架，但服务、端口与纪律独立。

- **拓扑限制**：现有连接为星形（从机只与主机直连）。互传只做**主机⇄从机双向**：主机可向任一已连接从机发送（OFFER 按目标编号定向下发，不广播）；从机只能向主机发送。**从机之间不互传、不经主机中转**（已知限制）。
- **新增消息（五种，走既有 WebSocket 通道）**：
  - `XFER_OFFER{ tid, from_no, token, files }`（发送方 → 接收方）：`tid` 为本轮随机串；`files` 为文件清单数组，每项 `{ name, size, sha256 }`，`size` 为字节数，`sha256` 为十六进制小写。`token` 为本轮文件服务的访问令牌（实现补充字段，接收方拉取时须回带，见下条）。接收方正有未决或进行中的接收时，对新提议自动回 `XFER_REJECT`；接收方 60 秒无人操作不自动处理，等用户裁决。
  - `XFER_ACCEPT{ tid }`（接收方 → 发送方）：接收方点「接受」后发送（首次接收需先完成落盘目录引导，引导回来后补发）；发送方收到后才启动本轮文件服务。
  - `XFER_REJECT{ tid }`（接收方 → 发送方）：点「拒绝」或忙时自动回绝；发送方收到后作废本轮（不启动服务或立即关停）。
  - `XFER_CANCEL{ tid }`（任一方 → 对方）：终止本轮；发送方关停服务，接收方作废拉取（已落 `.part` 保留待续传）。
  - `XFER_FILE_DONE{ tid, idx, ok }`（接收方 → 发送方）：接收方每处理完一个文件（成功落盘或失败终局）发一条，`idx` 为清单下标，`ok` 为布尔。
  - `XFER_DONE{ tid }`（接收方 → 发送方）：全部文件处理完（成功或失败）后发一条；发送方据此关停本轮文件服务并标记本轮完成。
- **拉取服务（发送方本轮临时 HTTP 服务）**：收到 `XFER_ACCEPT` 后启动，绑发送方本机局域网 IP 的 **18768** 端口（与媒体分发的 18767、WebSocket 的 18765 均区分）；路径为 `/xfer/<tid>/<idx>` 且查询参数须带 `?token=<本轮令牌>`，路径或令牌不符一律 **404**。支持 **Range** 三形式（`bytes=start-end`、只有起点、只有尾部）回 **206 + Content-Range**，无 Range 回 **200 + Content-Length**；每连接一线程。服务在本轮结束时关停（`XFER_DONE`、`XFER_CANCEL`、被拒绝、对端断开、或启动后 **10 分钟超时**），启停各写一行 `XFER` 日志。
- **接收拉取与 .part 纪律**：接收方逐个文件串行拉取（一个完再下一个）。每个文件先下到 App 外部目录的 `xfer` 子目录，半成品名 `<sha256 前 16 位>.part`（跨轮同名即同一文件）。开始拉取前先查同名 `.part`：长度小于目标 `size` 时以 `Range: bytes=<已收长度>-` 续拉并追加写；长度等于 `size` 时跳过下载直接进校验；长度大于 `size` 时删除重拉。拉取中断（网络错误、读超时）保留 `.part`，该文件标「中断待续」，本轮继续下一个文件。若服务端对带 Range 的请求回 200（未理会 Range），接收方整文件重写 `.part`。
- **校验与落盘**：`.part` 字节数等于 `size` 后计算 SHA-256：与清单一致才算成功——搬入目标文件夹并改正式文件名、删 `.part`、回 `XFER_FILE_DONE ok=true`；不一致则删 `.part`、整文件自动重拉一次，再不一致标失败、回 `ok=false`。**纪律：校验不过的文件不许落正式文件名。** 目标文件夹经 SAF：接收方首次接收时若未授权，点接受后先引导用户经 `ACTION_OPEN_DOCUMENT_TREE` 选一次文件夹（建议名「多屏互传」），授权持久化，后续接收直接落盘（经 DocumentsContract 在该目录建文件并流式写入）；未授权或用户跳过时，成品落 App 外部目录的 `xfer` 子目录，状态行明示落盘位置。文件名消毒：去掉路径分隔符、空名兜底；目标文件夹内同名已存在时依次追加「 (1)」「 (2)」。
- **进度与日志**：接收方逐行显示每文件已收字节百分比并有一行总进度汇总；发送方靠 `XFER_FILE_DONE` 更新清单行状态。两边关键节点各写一行 `XFER` 日志：offer 收发、accept/reject、每文件 start（含 `resume_from` 字节数）、每文件 done（含 `sha_ok` 与耗时）、fail 原因、服务启停。

## 13. v1.6 增补（v0.6.0 实现）

本节为 v0.6.0 的三项协议面变化，只增补；其中第一项**改写第 12 节的一处口径**（XFER 服务启动时机），其余各节不变。

- **XFER 服务启动时机改口径（覆盖第 12 节「收到 XFER_ACCEPT 后启动」）**：发送方改为在**发出 `XFER_OFFER` 的同时即启动**本轮文件服务（文件清单在发 offer 时已定，服务参数与第 12 节相同：绑局域网 IP 的 18768、路径 `/xfer/<tid>/<idx>`、令牌校验、Range 语义）。背景（真机实锤竞态）：旧口径下接收方发出 ACCEPT 后立即拉取，而发送方收到 ACCEPT 才启动服务，接收方的连接比服务监听早约 150ms 到达被拒，且一失败整轮判死；主机→从机方向的一次失败与从机→主机方向的连败均为此因。关停条件不变（`XFER_DONE`、`XFER_CANCEL`、被拒绝、对端断开、启动后 10 分钟超时）；收到 ACCEPT 时若服务未在运行，仅兜底补启。
- **接收方连接退避重试（新纪律）**：接收方拉取每个文件时，仅在「连接建立」阶段（拿到 HTTP 响应码之前）遇连接类异常（ConnectException、连接超时、无路由）才重试：300ms 起翻倍退避、单次上限 1200ms、至多 5 次尝试，总窗口约 3 秒，其间状态行与清单行显示「等待对方服务…」，每次重试记 `XFER connect retry tid idx attempt=N`。重试用尽才按第 12 节判该文件失败（保留 `.part`、标中断待续）。已开始读流后的中断不走本重试，仍按第 12 节 `.part` 纪律处理。
- **`duoping://` 连接串（扫码入会）**：主机大厅可显示连接二维码，内容为纯文本连接串 `duoping://<主机局域网IP>:18765/<会话令牌>`，其中端口为 WebSocket 端口（第 1 节），会话令牌沿用组会随机令牌机制（每次组会生成）；二维码下方同时显示 IP 与令牌文本，手输 IP 的既有入会方式不变。从机扫码识别到该串后解析出 IP，直接沿用既有 WebSocket 连接与 HELLO 入会流程（令牌本阶段仅随串携带，连接侧不校验，留作后续会话校验的占位）。扫码成功记日志 `JOIN qr ok ip=<ip>`，取消记 `JOIN qr cancel`。
- **`LAYOUT` 新增字段 `fit`**：`LAYOUT` 消息新增 `fit: "cover" | "contain"`，为全场显示模式，由主机选定随 LAYOUT 一并下发；**缺省（字段缺失）按 `cover` 解读，兼容旧端**。`cover`（铺满）＝现行语义：视频等比放大、按画布比例裁出可见子矩形，各机显示本机 tile 对应份，画面铺满屏幕；`contain`（完整）＝整幅视频等比放下：视频在画布内居中占据子矩形（宽高比取视频与画布中较紧的一边），各机 tile 与该子矩形交集之外的屏幕区域露舞台底色（#0B0B10），不许拉伸。两分支的 TRANSFORM 计算均保持等比（scaleX 恒等于 scaleY 的口径不变）与居中；主机侧 `LAYOUT` 日志行同步追加 `fit=<cover|contain>`，TRANSFORM 日志行格式不变。

## 14. v1.7 增补（v0.6.1 实现）

本节为 v0.6.1 的三项增补：新消息 `EXIT_PLAYBACK`、成员变化自动重排、`LAYOUT` 的 `fit` 字段由二档扩为三档（改写第 13 节的 fit 口径）。只增补，其余各节不变。

- **`EXIT_PLAYBACK{ client_no }`（CLIENT → HOST，新消息，走既有 WebSocket 通道）**：从机用户点本机「退出播放」时发送；该从机随即在本机退出播放模式（停本机播放器渲染、回本机面板/待机界面），**WebSocket 连接保持不断**，全场会话不受影响。主机收到后只做三件事：设备列表里该编号行状态改为「已退出播放」；状态行提示「N 号机已退出播放」；记日志 `HOST note client=<no> exit playback`。**主机不暂停、不做任何播放动作**——是否暂停由主机用户手动决定（明确口径，不许实现成自动暂停或任何连带播放控制）。该从机之后若重新走 PREPARE/READY/START 入场，主机在收到其 READY 时清除退出标记、该行状态恢复正常。
- **成员变化自动重排**：播放期间发生任一成员变化——收到 `EXIT_PLAYBACK`、某从机断开连接、已退出从机重新入场（重新 READY 并参与 START）——主机立即按**当前活跃成员集**（含主机本机，排除已退出/已断开者）重算布局并重发 `LAYOUT`；播放不中断、不重新备片（`LAYOUT` 即时生效为既有语义）。模式映射：沿用当前所选模式；该模式在新成员数下无定义时按就近规则回退——田字格（仅 4 台定义）在 3 台时回退横排三等分、2 台时回退横排；横排/竖排在任意成员数下保持同族重算；全屏跟随恒成立（单台时即全屏）。所选模式本身不被回退改写：成员数恢复后自动回到原模式。`fit` 选择在重排后保持不变、随新 `LAYOUT` 一并下发（下条的 contain_v 回落规则为例外）。每次重排记日志 `LAYOUT relayout reason=<exit|disconnect|rejoin> active=<编号列表> mode=<有效模式>` 一行。
- **`LAYOUT` 的 `fit` 字段扩为三档（改写第 13 节的二档口径）**：取值 `cover | contain_h | contain_v`，缺省（字段缺失）仍按 `cover` 解读、兼容旧端；第 13 节的旧值 `contain` 自本版起改名为 `contain_h`（收到旧值 `contain` 按 `contain_h` 解读，兼容 v0.6.0 端）。
  - `cover`（铺满）：现行语义不变——等比放大、裁切至铺满。明确口径：**铺满必然丢内容**，不得以「画面完整」描述此档。
  - `contain_h`（完整·横向）：黑边条＋整幅按宽放下（即原 `contain` 语义），任意布局可用。
  - `contain_v`（完整·竖向）：黑边条＋整幅**顺时针旋转 90°** 按屏幕长边放下（取向规则：恒顺时针，视频顶边落到屏幕右侧；用户将设备逆时针转 90° 即为正向观看）；竖屏单机看横屏片时画面利用最大。**只许用于单台全屏情形**（活跃成员恰 1 台）：多台布局下不提供该档；若当前所选为 `contain_v` 而活跃成员回到多台，随下一次 `LAYOUT` 自动回落 `contain_h` 并在主机状态行提示一行。视频与屏幕朝向已一致时不旋转（退化为 contain_h 的放法）。
  - 完整性口径：**「画面始终完整」仅在 `contain_h` / `contain_v` 下成立**；`cover` 下即使成员变化重排，画面仍裁切。重排只负责按活跃成员重算切片，不改变 fit 的完整性属性；三档的 TRANSFORM 均保持等比（scaleX 恒等于 scaleY，不变形的底线不因旋转改变）。

## 15. v1.8 增补（v0.6.3 实现）

本节为 v0.6.3 的一项增补：新消息 `STOP`。只增补，其余各节不变。

- **`STOP{}`（HOST → 全场广播，新消息，走既有 WebSocket 通道，无附加字段）**：语义＝**结束当前视频的播放会话**（「退出播放／退出此视频」）。与 `PAUSE` 的区别：暂停保留媒体与进度、可 RESUME；STOP 清除媒体，会话回待选片。与「结束会话」的区别：结束会话拆组会（停服务端、清连接、回角色选择）；STOP **不解散组会**——WebSocket 连接、设备编号、布局模式与 `fit` 选择全部保留，退出后重新选片即可再走 PREPARE→START 起播新片。
- **发起方**：仅主机可发。主机入口两处、同一处理：常显工具条「退出播放」按钮与面板「播放」页同名按钮；播放中、暂停中、已备片未起播、已播完任一状态可点，无播放会话时按钮不出现。主机发出时记日志 `STOP sent`，并对本机执行与从机相同的清除（下条）。
- **执行（各机同一口径，收到 STOP 的从机与主机本机均在主线程执行）**：停播放器并清除当前媒体与备片状态（prepared 置空、进度归零），作废进行中的分发下载；主机另停本场媒体分发服务（回空闲）并清就绪/失败表。从机执行后回待机大数字屏，状态行显示「等待主机选片」；主机执行后回大厅待选片状态。执行记日志 `STOP exec cleared=<true|false>`（cleared 表示执行前确有媒体在场）。执行幂等：本机已无媒体（含已本地退出播放的从机）再收到 STOP，只做状态复位、cleared=false，不报错。
- **与 `EXIT_PLAYBACK`（第 14 节）的分工**：EXIT_PLAYBACK 是从机对本机退出的自发通知（只退本机、主机只标记）；STOP 是主机对全场的结束当前视频指令（全场清媒体回待机）。从机执行 STOP **不回** EXIT_PLAYBACK，主机侧「已退出播放」标记不因 STOP 增减；从机本地「退出播放」小条是既有本地入口，与本消息无关。

## 16. v1.9 增补（v0.6.5 实现）

本节为 v0.6.5 的一项增补：设备编号的分配与释放口径（编号复用）。只增补，其余各节不变。

- **编号按连接分配（改写第 1 节的发号口径）**：主机处理 `HELLO` 时，为新连接分配**当前已连接从机未占用的最小正整数**（1 起；主机恒 0），随 `WELCOME{ client_no }` 下发。编号不再单调递增——同一连接存续期内编号不变，编号与物理摆位的对应在退出重进后仍可保持紧凑（编号定位是本协议的主定位手段，空号与跳号均属缺陷）。
- **断开释放、可复用**：从机连接断开（WebSocket 关闭）时，其编号即释放回池，后入会者可复用同一编号。编号与连接同生命周期，不为已断开设备保留。按编号索引的全部状态（就绪表、备片失败表、退出标记、设备尺寸、互传对端状态）随断开一并清理，复用该编号的新连接不继承前任任何状态。
- **退出播放不释放**：`EXIT_PLAYBACK`（第 14 节）只退播放、连接保持，该从机编号**不释放**；其重新入场（重新 READY/START）沿用原编号。
- **不变量**：任一时刻已连接从机的编号互不相同；布局、就绪判定与重排的活跃集口径（第 14 节）不变，仍以当前连接与标记的实时状态为准。

## 17. v1.10 增补（v0.7.0 实现）

本节为 v0.7.0 的一项增补：`PREPARE.url` 的取值来源扩展与播放侧请求头规则。协议不新增消息，解析是主机本地行为，其余各节不变。

- **`PREPARE.url` 可为 B 站解析后的 CDN 地址**：主机在「链接」入口收到 B 站形态输入（b23.tv 短链接、`bilibili.com/video/BV…` 链接、裸 BV 号、混有上述链接的 App 分享文本）时，先在主机本地完成解析（免登录、无 Cookie，桌面 UA＋Referer 调 `x/web-interface/view` 取 cid 与标题，再调 `x/player/playurl`（qn=80、fnval=1）取单文件 mp4 地址），随后与普通直链同路：主机本机以该地址备片，`PREPARE.url` 原样下发该 CDN 地址，从机以既有直链流式路径直接从 B 站 CDN 拉流播放。解析任一步失败，主机只在状态栏与日志报失败阶段（`BILI resolve fail stage=<redirect|view|playurl> code=<原始 code 或 http 状态>`），不发 PREPARE、不自动重试（上限 1 次，本版实现为 0 次）。成功记日志 `BILI resolve ok title=<标题> quality=<playurl 返回的 quality 数值> chost=<播放地址 host>`。解析所得地址随 B 站签名时效过期，口径与既有直链一致：建会解析、立即使用、不缓存。
- **播放侧请求头规则**：任一端（含主机本地备片）以 media3 播放时，若流地址的 host 含 `bilivideo` 或含 `upos`，数据源必须附加 `Referer: https://www.bilibili.com` 与桌面 Chrome UA（与解析侧同一 UA）——B 站 CDN 无此 Referer 回 403（实测：无 Referer 403、带 Referer 206）。其他来源地址（主机分发、普通直链、本地文件）不得附加这两个头。
